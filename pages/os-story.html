CH.00 / 序章

一台什么都没有的机器

在有操作系统之前，计算机是怎么工作的？它到底缺了什么？

想象你面前有一台刚出厂的计算机：一块 CPU，一条内存，一块磁盘。没有 Windows，没有 Linux，什么软件都没有。它能做的事情其实极其单纯——

CPU 一生只做一件事：从内存里取出一条指令，执行它，然后取下一条。取指、译码、执行，周而复始，每秒几十亿次。它不知道什么是"程序"，更不知道什么是"应用"，它只认识内存地址和指令。

那这样一台机器怎么跑程序？很简单：把程序的机器码放进内存，让 CPU 的指令指针指向第一条指令，它就跑起来了。早期的计算机确实就是这么用的——一次装一个程序，跑完，换下一个。这种时代甚至有个专门的名字：批处理。

听起来能用。但只要多用几天，三个致命问题就会浮出水面：

困境浮现

问题一：CPU 大部分时间在发呆。程序一旦去读磁盘，CPU 就只能干等——磁盘比 CPU 慢几百万倍。一台昂贵的机器，99% 的时间在等 I/O。

问题二：程序之间没有任何防护。如果内存里同时放两个程序，任何一个都可以随手改写另一个的内存，甚至改写机器的核心数据。一个 bug 就能带崩整台机器。

问题三：硬件太难用了。想往磁盘写点东西？你得亲自操纵磁盘控制器的寄存器、算扇区号、处理磁头移动。每个程序员都要重写一遍这些底层细节。

盯着这三个问题看，你会发现它们指向同一个缺口：机器和程序之间，缺一层"中间人"。这个中间人要做三件事：

  • 虚拟化（Virtualization）：把一个 CPU 变出"很多个"的假象，把一条内存变出"每人一份"的假象——解决独占和等待的问题；
  • 并发管理（Concurrency）：当多个执行流真的同时存在时，管住它们，别让它们互相踩踏；
  • 持久化（Persistence）：把"操纵磁盘寄存器"包装成"打开文件、写入、关闭"这样的人话。

这个中间人，就是操作系统（Operating System）。接下来的四章，就是它逐步长出这三种能力的故事。记住这条主线——整本操作系统教材，其实只回答三个问题：怎么虚拟化、怎么管并发、怎么做持久化。

CH.01 / 虚拟化 CPU

让 CPU 学会分身 —— 进程与调度

只有一个 CPU，却想"同时"跑几十个程序，这个魔术是怎么变的？

第一步：从"程序"到"进程"

先想最朴素的方案：让 CPU 跑一会儿程序 A，暂停，跑一会儿程序 B，再切回 A……切得足够快，人眼看起来就是"同时在跑"。这个思路叫时分共享（time sharing），方向完全正确。但立刻遇到一个具体问题：

暂停 A 的时候，怎么保证之后还能"原样"恢复它？

A 跑到一半，它的现场是什么？无非是：CPU 里各个寄存器的值（包括指令指针 PC——记录跑到哪一行了）、它的内存内容、它打开的文件等等。只要在暂停时把这些现场完整存下来，恢复时原样填回去，程序根本感觉不到自己被暂停过。

于是一个核心概念被逼出来了：

概念诞生

进程（Process）= 程序 + 它的运行现场。程序是静态的一堆指令（磁盘上的文件）；进程是这堆指令"活起来"之后的样子，包括它的寄存器值、它的内存（地址空间）、打开的文件列表。操作系统为每个进程维护一个记录本，叫 PCB（进程控制块），现场就存在这里。切换进程时保存旧现场、装载新现场的动作，叫上下文切换（context switch）。

第二步：谁来喊"停"？——从合作到抢占

现场能存了，下一个问题：切换的时机由谁决定？

天真方案：相信程序自己。约定每个程序跑一段就主动调用 yield() 交出 CPU。这叫协作式调度，早期的 Windows 3.x 和 Mac OS 9 真的就是这么干的。

翻车现场

某个程序写了个死循环 while(1);，它永远不会调用 yield——整台机器就此卡死，操作系统连插手的机会都没有。因为 OS 也只是内存里的一段代码，CPU 不跑到它头上，它就是死的。靠自觉，等于没有规则。

要打破僵局，必须有一个不依赖程序配合、能强行把 CPU 抢回来的机制。软件做不到（软件得先被执行才有话语权），所以只能求助硬件：

时钟中断（timer interrupt）。主板上装一个定时器，每隔几毫秒硬件强制打断 CPU，让它跳到操作系统预先登记好的一段代码去执行。这一跳，控制权就回到了 OS 手里——它可以决定：继续跑刚才的进程，还是换一个。这就是抢占式调度（preemptive scheduling）。

时钟中断是操作系统真正"掌权"的根基——没有它，OS 只是一个被程序召之即来挥之即去的函数库。

第三步：不能让程序为所欲为——用户态与内核态

还剩序章里的"防护"问题：进程要是自己去改时钟、直接操作磁盘、修改别人的内存怎么办？解决思路是给 CPU 设两种身份：

  • 内核态（kernel mode）：什么指令都能执行，操作系统的代码运行在这个身份下；
  • 用户态（user mode）：危险指令（操作硬件、改中断设置等）一执行就触发异常，普通程序被关在这个身份里。

可程序总有正当理由要做危险的事，比如读文件。怎么办？开一扇受控的门：系统调用（system call）。程序执行一条特殊的 trap 指令，CPU 自动切到内核态、跳到 OS 预设的入口；OS 检查请求是否合法，代为执行，再降回用户态把结果还给程序。

你平时写的 open()、read()、fork()，本质都是这扇门上的门铃。这套"平时受限运行、有事 trap 进门"的机制叫受限直接执行（Limited Direct Execution）——"直接"保证了效率（大部分时间程序直接在 CPU 上裸跑，没有中间层），"受限"保证了安全。

第四步：进程的一生——状态机

现在把视角拉远。任意时刻，一个进程处在什么状态？梳理一下无非三种：正占着 CPU 的（运行 Running）、随时能跑但还没轮到的（就绪 Ready）、在等某件事发生（比如磁盘读完）暂时跑不了的（阻塞 Blocked）。

这个状态机里藏着序章"CPU 发呆"问题的答案：当进程 A 阻塞在磁盘 I/O 上时，OS 立刻把 CPU 切给就绪队列里的 B——等待和计算被重叠起来，CPU 的空转消失了。这正是多道程序设计（multiprogramming）的全部意义。

Unix 的三板斧

在 Unix 世界里，进程的创建与运行由三个系统调用协作完成：fork() 把当前进程完整复制一份（父子进程从同一行代码继续，靠返回值区分彼此）；exec() 把当前进程的内容替换成另一个程序（脱胎换骨，进程号不变）；wait() 让父进程等子进程结束。你在终端敲 ls，shell 做的就是 fork 出一个分身，分身 exec 成 ls，shell 自己 wait——分离 fork 和 exec，正是为了让 shell 有机会在两步之间做重定向、管道这些小动作。

第五步：轮到谁跑？——调度策略的进化

机制（怎么切换）解决了，还剩策略（切给谁）。这是一条不断发现新矛盾的进化链，值得按顺序走一遍，因为每一种调度算法都是对前一种缺陷的直接回应：

策略思路翻车点 → 引出下一个
FIFO 先来先服务按到达顺序排队跑完短任务排在长任务后面干等（护航效应），平均周转时间惨不忍睹
SJF 最短任务优先先跑最短的长任务先到已开跑，短任务来了还是得等——需要抢占
STCF 最短剩余时间优先随时抢占，永远跑剩余最短的周转时间最优，但长任务可能饿死；而且交互程序响应差——没人愿意打字后卡三秒
RR 时间片轮转每人跑一小片，轮流来响应时间极好，周转时间变差；片太短则切换开销吃掉性能
MLFQ 多级反馈队列多层优先级：新任务放最高层，用满时间片就降级不需预知任务长短，用历史行为预测未来：交互型（常主动放弃 CPU）自然留在高层，计算型自然沉底。需定期整体提升防饿死
CFS 完全公平调度（Linux）记录每个任务的虚拟运行时间 vruntime，永远挑最小的跑用红黑树管理，把"公平"变成可计算的量；权重（nice 值）让 vruntime 走得快慢不同，实现优先级
思考方法

注意这条链上反复出现的张力：周转时间（吞吐）和响应时间（交互体验）是一对天生的冤家，优化一个必然牺牲另一个。工程里没有"最好的调度算法"，只有"最适合当前负载的取舍"。遇到任何调度类问题，先问：这个场景里，我更在乎哪个指标？

CH.02 / 虚拟化内存

给每个程序一个平行宇宙 —— 虚拟内存

几十个进程挤在同一条物理内存里，怎么让每一个都以为整条内存归自己？

第一步：为什么不能直接用物理地址

CPU 虚拟化解决后，内存里同时住着多个进程。如果程序直接使用物理地址，马上有两个灾难：其一，程序 A 一个指针越界就写坏了 B 的数据，毫无保护；其二，程序编译时写死的地址（比如"跳转到 0x4000"）要求它必须被装载到固定位置，两个程序想用同一个地址就打架了。

解决思路和 CPU 那章如出一辙：加一层翻译。程序看到的地址是假的（虚拟地址），每次访存时由硬件翻译成真实位置（物理地址）。每个进程拥有一套独立的翻译规则，于是每个进程都活在自己的"平行宇宙"里：它以为地址从 0 开始、整条内存归它——这套假象叫地址空间（address space），里面按惯例放着代码段、堆（向下长）和栈（向上长）。

第二步：翻译规则怎么设计？——三次迭代

迭代一：基址 + 界限寄存器。最简单的翻译：物理地址 = 虚拟地址 + 基址寄存器，同时检查不许超过界限。硬件便宜，切换进程时换一下寄存器就行。翻车点：每个进程必须占一段连续的物理内存，而堆和栈中间那一大块没用到的空隙也被白白占着；进程来来去去之后，内存里布满大小不一的空洞——外部碎片，明明总空闲够，却找不出一块连续的大空间。

迭代二：分段（segmentation）。那就别整段搬，把代码、堆、栈各自作为一个"段"，每段一对基址/界限，分开放置。空隙问题缓解了。翻车点：段仍然是大小不一的连续块，外部碎片依旧存在，只是从"每进程一个洞"变成"每段一个洞"。

迭代三：分页（paging）。问题的根源是"大小不一"。那就一刀切：把虚拟地址空间切成固定大小的页（page，通常 4KB），物理内存切成同样大小的帧（frame），任何一页可以放进任何一帧。大小全部相同，就不存在"放不进去"的洞——外部碎片被彻底消灭。每个进程配一张页表（page table），记录"我的第 N 页放在物理的第几帧"。

地址翻译的算术

一个 32 位虚拟地址、4KB 页的系统里，地址被拆成两半：高 20 位是页号（查页表用），低 12 位是页内偏移（原样保留）。翻译 = 用页号查页表得到帧号，帧号拼上偏移就是物理地址。页表项（PTE）里除了帧号还有几个关键标志位：有效位（这页在不在内存）、保护位(可读/可写/可执行)、脏位（被写过没有）、访问位（最近用过没有）——后面每一位都会派上用场。

第三步：两个新麻烦，两个经典解法

分页优雅，但自身带来两个代价，教科书里最重要的两个机制就是为它们生的。

麻烦一：页表太大。32 位地址空间有 2²⁰ = 100 万个页，每个进程一张百万条目的表，光页表就吃掉 4MB；64 位下更是天文数字。观察：绝大多数进程只用了地址空间的一小角，页表里 99% 的条目是无效的。解法：多级页表——把页表本身也切成页，再用一张"页目录"索引它们；整块无效的区域连页表页都不分配。用"按需生长的树"替代"一次铺满的数组"。x86-64 用的是四级页表，正在向五级演进。

麻烦二：访存次数翻倍。每次访问数据前得先访问内存里的页表（多级页表下是先访问四次！）。解法：TLB（Translation Lookaside Buffer）——在 CPU 里放一个小缓存，存最近用过的"页号 → 帧号"映射。命中（绝大多数情况）翻译零开销；未命中才去走页表。TLB 能救场，靠的是程序访存的局部性：刚访问过的页，马上还会被访问。

思考方法

停下来看这两个解法，你会发现它们是系统设计里出场率最高的两招：空间太大 → 用树状/稀疏结构按需分配；速度太慢 → 加缓存赌局部性。后面还会反复见到它们。

第四步：内存不够住怎么办？——把磁盘拉进来

所有进程的地址空间加起来远大于物理内存，怎么圆这个谎？答案藏在页表项的有效位里：不常用的页可以被搬到磁盘上（交换空间 swap），页表项标记为"不在内存"。当进程访问到这样的页，硬件翻译失败，触发缺页中断（page fault），OS 接管：从磁盘把这页读回内存、更新页表、重新执行那条指令——进程全程无感，只觉得那次访问慢了一点。

内存满了要腾地方，踢谁出去？这就是页面置换算法：

  • 最优算法（OPT）：踢"将来最久不会被用到"的页——需要预知未来，不可实现，只做基准；
  • FIFO：踢最早进来的——简单，但可能踢掉常用页，甚至出现"内存越大缺页越多"的 Belady 异常；
  • LRU：踢最久没用过的——用过去预测未来，效果好，但精确实现要每次访存都记时间戳，太贵；
  • 时钟算法（Clock）：LRU 的廉价近似。所有页排成一圈，利用硬件自动设置的访问位：指针扫过，访问位是 1 就清零放过，是 0 就淘汰。真实系统用的都是这类近似 LRU。
警示：抖动

如果进程实际需要的页远多于物理内存，就会陷入"刚踢出去的页马上又要用"的死循环，CPU 时间全花在换页上，系统吞吐断崖式下跌——这叫抖动（thrashing）。此时唯一的出路是降低并发度（挂起一些进程）或加内存，调度算法救不了。

第五步：虚拟内存的红利——惰性的艺术

这套"访问时才处理"的机制一旦建成，很多昂贵操作都可以变成"先记账、用到再说"：

  • 写时复制（Copy-on-Write）：fork() 并不真的复制内存，父子共享所有页、全部标记只读；谁先写，谁在缺页中断里获得自己的副本。fork 因此快如闪电；
  • 按需加载（demand paging）：exec 一个大程序不必整个读入，跑到哪页加载哪页；
  • 内存映射文件（mmap）：把文件"假装"成一段内存，读写内存即读写文件，加载同样是惰性的。

虚拟内存的精髓可以浓缩成一句话：用"地址翻译 + 缺页中断"这一对钩子，把内存管理的所有决策推迟到最后一刻。

CH.03 / 并发

当分身开始打架 —— 并发与锁

多个执行流共享同一份数据时，为什么连 counter++ 都会算错？又该怎么救？

第一步：线程为什么会出现

进程隔离得很好，但隔离也是墙：两个进程想协作干一件活（比如一个网页服务器同时处理一万个请求），进程间通信又慢又麻烦，而且每个进程都背着一整套地址空间，创建和切换都重。

需求其实是："我要多个执行流，但它们操作的是同一份数据。"于是把进程一拆为二：地址空间、打开的文件这些资源归进程；执行流本身（寄存器 + 栈）单独抽出来，叫线程（thread）。同一进程的多个线程共享全部内存，只有各自的栈和寄存器是私有的。切换线程不必换地址空间，轻快得多。

第二步：共享的代价——一行代码的车祸

共享内存带来了协作的便利，也带来了操作系统里最阴险的一类 bug。看这个实验：两个线程各把共享变量 counter 加一百万次，最后结果却几乎从不等于两百万。

翻车现场

counter++ 在 CPU 眼里是三条指令：读 counter 到寄存器 → 寄存器加一 → 写回内存。假设 counter=50，线程 A 读到 50、加成 51，还没写回——时钟中断，切到线程 B。B 也读到 50，加成 51，写回。切回 A，A 把自己的 51 也写回。两次加一，counter 只增加了 1。结果取决于中断切换的精确时机，每次跑都不一样——这叫竞态条件（race condition），这类结果依赖时序的代码段叫临界区（critical section）。

问题的本质：三条指令的组合不是原子的，中间可以被任意打断。我们需要的性质是互斥（mutual exclusion）——同一时刻至多一个线程身处临界区。

第三步：锁怎么造出来

把互斥包装成一对操作：进临界区前 lock()，出来后 unlock()，有人持锁时别人 lock 就得等。接口好定，难在实现——这又是一条"天真方案逐步翻车"的链：

  • 尝试一：关中断。进临界区前关掉中断，没人能打断我。单核确实有效，但：用户程序若能关中断，就能独霸 CPU（回到协作式时代的噩梦）；而且多核下完全无效——别的核根本不受你这个核的中断开关影响；
  • 尝试二：用一个 flag 变量标记"有人在里面"。检查 flag 和设置 flag 是两步，这两步之间同样能被打断——用有竞态的代码去解决竞态，循环论证；
  • 破局：硬件出手。软件在"检查+修改"之间怎么都会留缝，那就让硬件提供一条一步完成"读出旧值并写入新值"的原子指令——test-and-set（或 compare-and-swap）。用它写 while (test_and_set(&flag) == 1) ; 就是一把正确的自旋锁（spinlock）。

自旋锁正确了，但等锁的线程在空转烧 CPU。改进：拿不到锁就把自己标记为阻塞、让出 CPU，由持锁者释放时唤醒——这是互斥锁（mutex）的睡眠实现。两者的取舍很典型：临界区极短用自旋（省去两次上下文切换），可能等很久用睡眠。Linux 内核里两者都在用。

第四步：光有互斥不够——条件变量与信号量

很快你会发现另一类需求锁解决不了：线程 A 要等某个条件成立才能继续（队列里有数据了、子任务完成了）。拿着锁死等？别人永远没机会把条件变成真。反复加锁解锁轮询？浪费且有延迟。

正确的原语是条件变量（condition variable）：wait(cond, lock) 原子地"释放锁并睡去"，被 signal(cond) 唤醒后重新拿锁继续。"释放锁"和"睡去"必须是原子的一步，否则会在缝隙里错过唤醒信号，睡死过去。

经典模型：生产者-消费者

一个有界缓冲区，生产者往里放，消费者往外取：缓冲区满，生产者睡；空，消费者睡。所有消息队列、线程池、管道的内核都是它。两条铁律：wait 必须包在 while 循环里重新检查条件（被唤醒 ≠ 条件仍然成立，可能被别人抢先消费了）；生产者和消费者要用两个条件变量（"有空位"和"有数据"），混用一个会唤错对象导致全体沉睡。

信号量（semaphore）是另一套等价的原语：一个带计数的对象，P() 减一、减到负就睡，V() 加一并唤醒一个。初值为 1 就是锁，初值为 N 就是"最多 N 人同行"的资源计数器。锁 + 条件变量能做的，信号量都能做，反之亦然——面试爱考互相实现。

第五步：终极噩梦——死锁

锁多了，新的灾难登场：线程 1 持有锁 A 等锁 B，线程 2 持有锁 B 等锁 A——两人永远互相等待，这就是死锁（deadlock）。死锁的成立需要四个条件同时满足，破坏任何一个即可预防：

必要条件含义破坏它的办法
互斥资源一次只能一人用用无锁数据结构（CAS）绕开锁
持有并等待拿着一个还要等下一个一次性申请全部资源，拿不齐就全放掉
不可抢占资源不能被强行夺走trylock 失败就释放已持有的锁重来
循环等待等待关系成环给所有锁定全局顺序，人人按序加锁——工程上最常用

除了预防，还有两条路线：避免（调度时算一算会不会进入危险状态，如银行家算法——理论经典，工程少用）和检测恢复（定期找等待环，找到就杀掉一个，数据库死锁处理就是这么干的）。

思考方法

并发这一章的审题习惯：看到任何共享数据，先问三个问题——谁在同时碰它？操作是原子的吗？我等待的条件可能在检查后、行动前被别人改掉吗？绝大多数并发 bug 都栽在第三问：check 和 act 之间的缝隙（TOCTOU）。这个习惯和你写算法时"先想清不变式再动手"是同一件事。

CH.04 / 持久化

对抗断电与遗忘 —— 文件系统

内存一断电就清零。怎么把数据可靠地留在磁盘上，还要在写到一半断电时不留下烂摊子？

第一步：和一个慢得离谱的设备打交道

磁盘的世界观和内存完全不同：它按扇区（512B/4KB）整块读写，机械盘还要等磁头寻道、盘片旋转，一次随机访问几毫秒——比内存慢十万倍。第一个问题是CPU 怎么跟这种慢设备沟通，答案又是一条进化链：

  • 轮询（polling）：CPU 不停地问"好了没？"——把 CPU 拴在了慢设备上；
  • 中断（interrupt）：CPU 发完命令去干别的，设备完成后用中断"喊"它——CPU 解放了，但数据搬运（一个字节一个字节从设备拷到内存）还得 CPU 亲自动手；
  • DMA：再雇一个专职搬运工（DMA 控制器），CPU 只说"把这块数据搬到那个地址"，搬完中断通知——CPU 彻底只管指挥，不碰数据。

第二步：从扇区到文件——inode 的设计

裸磁盘只是一个巨大的扇区数组，人类需要的却是"文件"和"文件夹"。文件系统要回答的核心问题是：拿什么数据结构，把"文件名 → 磁盘上的一堆块"这个映射管起来？

Unix 的答案优雅而长寿：

概念诞生

inode：每个文件一个"档案卡"，记录文件的元数据（大小、权限、时间戳）和它的数据块都在磁盘哪些位置。前几块用直接指针记录，大文件用上间接指针——指向"装满指针的块"，再不够用二级、三级间接指针。又是那棵"按需生长的树"（和多级页表同一招）。目录本身也是文件，内容就是一张"文件名 → inode 号"的表。文件名不属于文件，属于目录——所以硬链接（两个名字指向同一 inode）才成为可能，inode 里的链接计数归零、且无人打开时，文件才真正被删除。

于是打开 /home/zx/notes.txt 的全过程是一次逐级查表：读根目录 / 的 inode → 找到目录数据 → 查到 home 的 inode 号 → 读它 → 查到 zx → 再查到 notes.txt 的 inode。拿到 inode，就拿到了文件的一切。

性能上还有一层要紧的设计：磁盘随机访问太贵，所以 FFS（快速文件系统）开始，文件系统都在拼命制造局部性——把同一目录的文件、文件的 inode 和它的数据块，尽量放进磁盘上相邻的块组里；同时内存里用页缓存（page cache）兜住热数据，读写先走内存。这就是为什么 write() 返回了数据却可能还没落盘——真要保证落盘，必须显式调用 fsync()，数据库的日志写入从不省这一步。

第三步：最难的问题——写到一半断电了

往文件追加一个块，文件系统实际要写三处：数据块本身、inode（新指针和新大小）、位图（标记块已占用）。磁盘一次只能原子地写一个扇区，三笔写之间断电，就会留下各种不一致：位图说块被占了却没人用（漏块）、inode 指向了没写入的垃圾数据（更糟）。这就是崩溃一致性问题（crash consistency）——文件系统领域几十年的主线剧情。

  • 方案一：事后打扫（fsck）。崩溃重启后全盘扫描，检查所有 inode 和位图是否自洽，能修则修。翻车点：磁盘越来越大，扫一遍要几小时；而且它只能修"账目不平"，救不回指向垃圾数据的 inode；
  • 方案二：先记账再动手——日志（journaling）。借用数据库的预写日志思想：把这次要做的所有修改先完整写进磁盘上一块专门的日志区，写一条"记账完毕"的提交记录，然后才去改真正的位置。断电了？重启时看日志：有完整提交记录的事务，照着日志重放一遍；没写完提交记录的，整个当作没发生。无论断电落在哪一刻，结果要么是"全做了"要么是"全没做"——原子性诞生了。ext4、NTFS、XFS 都走这条路（多数默认只对元数据记日志，性能与安全的折中）；
  • 方案三：永不覆盖——写时复制。ZFS、Btrfs 更激进：任何修改都写到新位置，最后原子地切换一个根指针。老数据永远完好，还顺手得到了快照功能。
思考方法

"多步操作 + 中途可能崩溃"是分布式系统、数据库、文件系统共享的母题，解法也共享：要么先写日志（WAL），要么写新不改旧最后切指针（COW）。在操作系统里学会这两招，数据库的 redo log 和 MVCC 就只是老朋友换了名字。

CH.05 / 终章

开机之后的一秒钟

把四章的知识串成一条线：从按下电源键，到你在 shell 里敲下一条命令，发生了什么？

  1. 加电。CPU 从固定地址开始执行固件（BIOS/UEFI），固件找到磁盘上的引导程序，引导程序把内核装进内存并跳过去——此刻机器上只有一个执行流，运行在内核态；
  2. 内核初始化。建立页表、打开虚拟内存，登记中断处理程序（时钟、键盘、磁盘各就各位），初始化调度器和页缓存；
  3. 第一个进程。内核创建 1 号进程 init（如今多是 systemd）并降到用户态——从此内核退居幕后，只在中断和系统调用发生时被唤醒。init 再 fork 出登录程序、图形界面、你的 shell；
  4. 你敲下 python solve.py。每一次按键都是一次键盘中断；shell 被唤醒读入字符。回车后，shell fork()——写时复制让这次复制几乎免费——子进程 exec() 装载 Python，按需加载意味着解释器的代码页要跑到才从磁盘读入，每次都触发一次缺页中断；
  5. 程序运行。Python 读取脚本文件：read() 系统调用 trap 进内核，文件系统沿着目录一路查到 inode，发现页缓存没有，向磁盘发出 DMA 请求，进程阻塞——调度器立刻把 CPU 切给别的就绪进程。数据到了，磁盘中断唤醒它，回到就绪队列等待被选中；
  6. 结果落盘。脚本把答案写进文件：数据先进页缓存就返回了；文件系统在后台把这次修改先写日志、再写原位——就算此刻你一脚踢掉电源，重启后磁盘依然自洽。

数一数，这一秒钟里出场的角色：进程与 fork/exec、上下文切换与调度、用户态/内核态与系统调用、页表/TLB/缺页中断/写时复制、中断与 DMA、inode/页缓存/日志——四章的每一个概念都不是孤立的知识点，而是同一台机器上互相咬合的齿轮。

全书只有一句话

如果把整个操作系统压缩成一条思维主线，它是：硬件只提供了极少的原语——原子指令、中断、地址翻译、trap——操作系统用这几块积木，搭出了"每个程序独占一台无限大的机器"这个宏大的假象。

而贯穿始终的思考方法，值得你带去任何系统设计场景：

  • 先造机制，再谈策略——"怎么切换"和"切给谁"永远分开设计；
  • 加一层间接性能解决大多数问题（虚拟地址、inode、文件描述符都是间接层）；
  • 用缓存赌局部性对抗慢（TLB、页缓存），用按需生长的树对抗大（多级页表、间接块）；
  • 把多步操作变成"全或无"对抗崩溃（日志、写时复制）；
  • 遇到共享数据，永远先问：检查和行动之间，世界会不会变？

想继续深入，最贴合这种"问题驱动"叙事的教材是 Operating Systems: Three Easy Pieces（OSTEP，免费在线，有中文版《操作系统导论》）——本文的骨架就与它同源。配合动手：读 xv6 的源码，或在 Linux 下用 strace 观察任何命令背后的系统调用，齿轮会转得更清楚。
